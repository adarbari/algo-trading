# ADR 0024: API v1, a read-only FastAPI over services

**Status:** accepted (2026-10-03); amended by [0029](0029-rule-screener.md) (user
configs written only through `services/authoring`) and by [0028](0028-ibkr-enrichment-source.md) (the live-quote log); amended by [0037](0037-domain-read-model-served-by-graphql.md) (page reads move to a GraphQL layer over `services.read`; REST keeps writes, jobs, health, live, files); its "Explore queries" section is superseded by 0037 (read-model PR 10b deleted `services/explore`, 2026-10). Implements the `apps/api` part of
[0004](0004-apps-and-shared-libraries.md); reads under [0007](0007-point-in-time-data.md),
[0015](0015-configs-selections-users.md) (configs, users) and
[0019](0019-ownership-and-boundaries.md) (one owner per responsibility). Code:
`apps/api/algotrade_api/` (`src/algotrade/services/explore/` until read-model PR 10b).

## Context
The web app (`apps/web`, built separately) has to show everything built so far: nightly runs,
the universe and review lists, instruments with bars, events and features, option chains, the
feature catalogue, screens, backtests and configs. ADR 0004 makes `apps/api` its only backend
and `services/` the real interface, but no HTTP layer existed, and several reads a page needs
(a run's failures grouped, a feature's distribution, one instrument's latest features) had no
service. The API must not grow business logic, must not touch storage or `algotrade.data`
directly, and must never write.

## Decision
### HTTP layer
- `apps/api/algotrade_api/` is a uv workspace app (`algotrade-api`; FastAPI, uvicorn and
  pydantic v2 are its own dependencies, never the library's). `main.create_app(settings,
  store=None)` builds the app: CORS for the local web dev server (GET only), and error
  handlers mapping `NotFoundError` / `MissingDataError` to 404 and `ConfigurationError` to 400.
- `routes/<area>.py`: one router per area (health, explore, universe, instruments + chains,
  features, screens, backtests, configs; admin and runs under `/admin/`). A route is thin:
  parse parameters, call **one** `services.explore` function, map the dataclass it returns to
  a response schema
  (`Schema.model_validate(result)`). No business logic, no pandas.
- `schemas/<area>.py`: pydantic response models with `from_attributes`. They are the public
  contract: OpenAPI (`GET /openapi.json`) → `apps/api/openapi.json` (committed, written by
  `scripts/export_openapi.py`; a test fails when it is stale) → the web's generated TS client.
- `deps.py`: `ApiSettings` from the environment through `config.env` (`ALGOTRADE_DATA_URL`,
  `ALGOTRADE_CONFIG_DIR`, `ALGOTRADE_USER`: one local user until identity arrives) and the
  store, opened once per app (`Store` dependency).
- `algotrade-api` serves it with uvicorn on 127.0.0.1:8000 (`--reload` for development).
- v1 is **read-only and JSON**: every area reads point in time; `?date=` defaults to the
  latest session the area has; large lists are paged (`page`, `size` ≤ 1000).
- Paths follow the web app's two workspaces. Trader pages use area paths (`/explore/...`:
  the ticker table with any catalogue columns, compare features and rebased prices;
  `/universe`, `/instruments`, `/chains`, `/features`, `/screens`, `/backtests`, `/configs`).
  **Admin-only endpoints live under `/admin/`** (ingestion completeness and drill-down, run
  records, review lists), so role-gating can attach to one prefix when identity arrives.

### Explore queries

> **Superseded by [ADR 0037](0037-domain-read-model-served-by-graphql.md)** (read-model PR
> 10b): `services/explore` is deleted. Page reads are domain read objects in `services/read`
> served by GraphQL, for one resolved session (ADR 0036); the Builder's dry runs live in
> `services/preview`; `ReadStore` / `open_store` are API wiring in `apps/api/algotrade_api/deps.py`.
> Kept below as the record of v1.

- `src/algotrade/services/explore/` holds the read-only queries apps display, one module per
  area (at most 10), returning plain dataclasses of JSON-safe values. `store.ReadStore` is what they read
  (a `StoreReader`, the `ConfigStore` and the user); `open_store(url, config_dir, user)`
  opens it, so the API never imports `algotrade.storage`.
- Market data is read through `algotrade.data` (extended where a page needed it:
  `prices.adjusted_bars`, `rollups.rollup_row`, `rollups.rollup_rows(instruments=)`). The
  explore `features` and `instruments` modules read stored group rows with `rollup_rows` for
  display (a series, a distribution), never as feature inputs: they are `allowed` under
  `feature-input-loading` (ADR 0023) for that reason. Run
  records through `StoreReader.runs` / `StoreReader.run`, never by importing the ingestion
  app. A run's items are summarised by status code and failures grouped by normalised reason
  with examples by `services/run_items.py`, moved out of the nightly email report
  (`workflows/nightly/report.py`) so the report and the API group the same way.
- Which partition a `?date=` sees is `data.reference.snapshot` (latest on or before the
  date); for non-snapshot tables (chains, results) a date before the first partition is a
  404, never a later partition.
- Ingestion completeness (`explore/ingestion.py`): per dataset (reference, universe, bars,
  chains, every registered rollup) and exchange session, rows present against expected: the
  dataset's previous stored session for bars and rollups (a drop is the signal, as in the
  quality checks), the optionable universe for chains (`chains/status` OK), and for snapshot
  tables whether a snapshot was built or an earlier one is carried. The drill-down groups the
  items that are not OK by reason (chains: per underlying from `chains/status`; others: the
  writing runs' items).
- Feature catalogue: every selectable field (`services.configs.field_catalog`), with the
  per-feature metadata of ADR 0023 (`features.registry.feature`: kind, unit, description,
  null meaning, valid range, categories, inputs, version, group).

### Boundaries (import-linter)
(As of read-model PR 10b: "API: routes reach the library only through services.read,
services.preview, services.authoring, config and core"; "Preview is read-only" replaces
"Explore queries are read-only"; `explore-queries` is gone from ownership.)
- "API: routes reach the library only through services.explore, config and core": no
  `storage`, `data`, `engines`, `features`, `strategies`, `quant`, `analytics`, no write
  use cases (`services.jobs`, `backtests`, `screening`, `evaluation`), no pandas / numpy.
- "Explore queries are read-only": no `storage.tables.writers`, `result_writer` or
  `services.jobs`.
- `algotrade_api` joins "Apps never import each other" and "Shared libraries never import
  apps". Ownership: `http-api` (`apps/api/algotrade_api/*`) and `explore-queries`
  (`services/explore/*`).

## Consequences
- The web app has one typed, versioned contract; a schema change shows up as an
  `openapi.json` diff in review, and the client is regenerated from it.
- New pages add a query in `services/explore/<area>.py` (or a new area module), a schema and
  a thin route (`.claude/skills/add-api-endpoint`). Writes (submitting jobs) come later
  through `services.jobs`, as their own decision.
- Reads are as fast as the store: a whole-partition table (option quotes) is read and then
  filtered by underlying. A query engine (DuckDB, phase 6) can replace that under `data/`
  without touching the API.
